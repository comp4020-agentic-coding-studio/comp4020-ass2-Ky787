Nothing is obfuscated this week. That is deliberate: you cannot tell what an
obfuscator did to a program until you can tell what a *compiler* did to it,
and the compiler already did a great deal.

This page also hands you the vocabulary the rest of the course runs on. If you
have read compiler output before, you will skim the grey boxes. If you have
not, they are the page.

## Start with the program

We spend the whole semester on one small C file. Here is the function this
week is about, in the form its author wrote it:

<EvidenceCode
  id="assets/source/showcase.c"

  note="what the author wrote"
  fromMatch={/^    value\[0\] = input \+ 0x01010101u;$/}
  take={8}

Eight array slots, each getting the argument plus a different constant. Later
in the same function each slot is XORed with `0x12345678`, then has `0x1337`
added, then has `0x1111` subtracted, and finally all eight are XORed together
into the return value. No loops, no branches, no calls. You could work out what
it returns on paper.

That is the whole point of it. Everything this course shows you happens to a
function you could have written in a first-year lab.

"Frozen" is doing real work in that table. Because the source was fixed before
anything was built from it, no difference between two of this course's binaries
can be a difference in the program. When the machine code changes, something
changed it — and that is the only explanation available. You will not get that
luxury on real software.

## The compiler's own version

A compiler does not go straight from C to machine code. It first rewrites the
program into an **intermediate representation** — a form that is still
structured and typed, but much closer to what a machine does. Clang's is called
LLVM IR, and it is the thing every obfuscator in this course except one acts
on.

Before you read any: four words.

<Primer
  terms={[
    { term: "%0, %4, %5", gloss: "Values, not variables. Each one is <em>assigned exactly once</em> and never changes — a discipline called SSA. So <code>%5</code> is not a box; it is the name of one particular result." },
    { term: "alloca", gloss: "Reserve space on the stack, and give me a pointer to it. An array or an address-taken local becomes one of these." },
    { term: "getelementptr", gloss: "Compute the address of an element inside that space. It only does the arithmetic on the pointer — no memory is touched." },
    { term: "store volatile", gloss: "Write to memory, and <em>do not optimise this away</em>. The source declares the array <code>volatile</code> on purpose, so the compiler cannot collapse the whole function into its answer." },
  ]}
/>

## What the machine actually gets

One more step down. The **back end** turns IR into instructions for a specific
processor — choosing which machine instruction implements each IR operation,
a step called **instruction selection** — and a disassembler turns the
resulting bytes back into something readable.

Four more words, then the listing.

<Primer
  title="How to read a disassembly listing"
  terms={[
    { term: "140001030:", gloss: "The address this instruction lives at when the program is loaded. The left-hand column of every listing in this course." },
    { term: "05 01 01 01 01", gloss: "The actual bytes. This is the program — everything to the right of it is the disassembler being helpful." },
    { term: "immediate", gloss: "A constant baked into the instruction itself rather than fetched from memory. <code>0x1010101</code> here is an immediate, and it is stored least-significant byte first." },
    { term: "RVA", gloss: "The same address with the load address subtracted off — so <code>0x140001030</code> becomes RVA <code>0x1030</code>. Two runs of a program can load it in different places; the RVA does not move, which is why every specimen in this course is navigated by one." },
  ]}
/>

<EvidenceCode
  id="assets/evidence/baselines/ollvm16/demo_substitution_disassembly.txt"
  lang="asm"
  title="clean x64 — demo_substitution, starting at address 0x140001030"
  note="what the machine will execute"

Each site is three instructions: reload the argument from the stack, add the
constant, store it back into the slot. Notice `05 01 01 01 01` — that is
`add eax, 0x01010101`, with the constant you wrote sitting in the instruction
stream, backwards.

That is the first useful fact about machine code for an analyst. **Constants
are landmarks.** They are how you find the same computation again after
somebody has rearranged everything around it.

:::warning[A landmark is not a proof]
Finding `0x12345678` in a binary tells you where to look. It does not tell you
that the operation around it is still the one the source wrote, and from week 3
onward it frequently will not be.
:::

## The fourth description, and the last two words

There is one more way to describe this function, and it is the one the second
half of the course lives in.

<Primer
  title="The vocabulary weeks 6 to 10 are built on"
  terms={[
    { term: "basic block", gloss: "A run of instructions with one way in and no branching in the middle: once it starts, all of it runs. A block ends where control can go somewhere else." },
    { term: "control-flow graph", gloss: "Blocks as nodes, possible jumps as arrows. It is the picture of <em>what can run after what</em> — and it is <em>recovered</em> by a tool, not stored in the file." },
  ]}
/>

`demo_substitution` has no branches at all, so its control-flow graph is a
single basic block with nothing pointing out of it. That is unusual and it is
why this week starts here: with the graph out of the way, the only thing that
can change between two versions of this function is the arithmetic.

From week 6 the reverse is true — the arithmetic barely moves and the graph
explodes. Holding those two apart is most of the skill.

</section>

## The counts do not agree, and that is the point

The same function, measured three ways in the retained build matrix:

<Numbers
  items={[
    { value: "155", label: "LLVM IR instructions in the clean target", source: "showcase_matrix_v1 — O0 comparison table" },
    { value: "115", label: "x64 machine instructions in the same function", source: "showcase_matrix_v1 — O0 comparison table" },
    { value: "467", label: "bytes of machine code, first byte to last", source: "showcase_matrix_v1 — O0 comparison table" },
    { value: "51", label: "machine instructions for the same function at -O1", sourceId: "assets/reports/optimization_survival.md" },
  ]}
/>

One function; four numbers, all correct. The IR count is higher than the
machine count because IR spells out addressing that one x64 instruction does
for free. The `-O1` count is less than half the `-O0` count because at `-O0`
the compiler reloads the argument from the stack for every single site, and at
`-O1` it stops bothering.

This is the measurement discipline the rest of the course depends on. Whenever
you meet a number about a program, three questions come before believing it:
**which representation, which counting convention, and against which
comparator at which optimisation level.**

</section>

## Where an obfuscator can get in

You now have all four descriptions, which means you can be told the shape of
the whole course. An obfuscator picks one of them to change:

<LectureTable id="01_transformation_layers" class="sc-wide" />

The last column is the one to hold on to. A source-level transformation has to
survive the entire compiler after it; an IR-level transformation has to survive
the back end; a post-link transformation has no optimiser after it at all. In
week 5 we will find that this difference decides whether some transformations
exist in the final binary at all.

</section>

## Studio: find a constant, then follow its meaning

Working from the four files below, and nothing else:

1. Pick one of the eight XOR sites. Locate it in the C, in the IR, and in the
   disassembly. Write down the line or address of each.
2. Say what the compiler added around it that the author did not write, and why
   each addition is there. The grey boxes above are enough to answer this.
3. `demo_substitution` contains more than twenty-four operations. Twenty-four
   of them are the repeated sites the corpus was designed around; the rest are
   setup and the final reduction. Mark which is which, and say how you decided.
4. One sentence, to be repeated all semester: *what would have to be true for
   my answer to step 1 to be wrong?*

Bring the answers to step 3 and step 4. Step 3 is where people disagree, and
the disagreement is the useful part — the corpus documentation says
"twenty-four sites" and does not mean "twenty-four instructions".
