One tool, unmodified, pointed at four flattened functions from four
implementations. It is a reasonable tool built on a reasonable idea: discover
the dispatcher, recover each region's successors by symbolic execution, then
patch the binary so the blocks jump to each other directly.

Four runs. Four different kinds of outcome.

## The scoreboard, before anything else

Two working rewrites, one wrong answer, one no-output. Keep the third and
fourth rows apart in your head — they are different failures with different
causes, and treating them as one is the most common misreading of this table.

## The two that worked

<Numbers

/>

Both produced working executables: the canonical run prints all six expected
values and exits zero. The transfer is genuine — the tool was built against one
implementation and worked unmodified on another — and it is bounded, because
those two implementations share a lineage, a dispatcher shape and a state
layout.

The fourth number is the interesting one. The rewritten function has 17 blocks;
the compiler's own clean build of the same source has 21. The recovered version
is *smaller than the original*, keeps dead state writes that no longer control
anything, and is correct on every retained test. Graph identity was never the
goal and would have been the wrong goal.

The four legitimate `switch` alternatives were grouped under a single incoming
state. The recovery trace records one edge where the ground-truth region map
has four, and the patcher faithfully emitted what the trace told it. Note the
four `MOV DWORD PTR [RSP + 0xC], 0x24E` stores in the right-hand listing —
the same "next state" written four times, which is the fingerprint of the
collapse.

:::error[The point of the whole course, in one specimen]
The graph got 82% smaller. The file is structurally valid. The tool exited
zero. The successor score had already said 14 of 22 with one false pair —
*before anyone ran the binary*. And the thing that actually caught it was
running the program and comparing eight hex digits.

Nothing about the appearance of the output distinguishes this from the two
successes above.
:::

## The one that failed before it started

The fourth run is a different kind of negative result, and confusing it with
the third would be a mistake.

<EvidenceCode
  id="assets/evidence/s08_tigress_flatten/stock_result.json"

  title="stock_result.json — the whole outcome"
  note="read the stderr line"
  fromMatch={/"exit_code":/}

/>

`INFO:root:Function 0x140001020 is not flattened.` No output file. No patch. No
symbolic execution, no solver, no successor recovery — the tool's *discovery*
stage saw six blocks where the jump-table-aware reference has 38, decided this
was not a flattened function, and stopped.

<Numbers
  items={[
    { value: "6", label: "blocks the stock discovery stage found", sourceId: "assets/evidence/s08_tigress_flatten/before_cfg.txt" },
    { value: "38", label: "blocks in the jump-table-aware reference for the same function", sourceId: "assets/evidence/s08_tigress_flatten/reference_complete_cfg.txt" },
    { value: "21", label: "dispatch targets it never saw, behind one indirect jump", sourceId: "assets/evidence/s08_tigress_flatten/verified_jump_table.json" },
    { value: "0", label: "solver queries issued — the failure is upstream of the analysis", sourceId: "assets/evidence/s08_tigress_flatten/stock_result.json" },
  ]}
/>

Six discovered blocks is not a six-block function. It is a graph with 32
missing blocks, because the edges out of the dispatcher go through an indirect
jump and resolving those needs a jump-table model the discovery stage does not
have. A disassembler with that model resolves them; this tool does not.

So the honest verdict is "blocked at discovery", not "the symbolic execution
failed" and certainly not "the solver could not handle it". Lowering the
acceptance threshold does not help either — a separately labelled scoring
adapter was tried and also fails, which is what you would expect when the
problem is 32 absent blocks rather than a score.

## What the four outcomes have in common

Each of the four runs used the same tool with the same defaults, and the
difference between them is an assumption about the representation:

- the two successes share the dispatcher shape and state layout the tool was
  written against;
- the wrong rewrite shares the shape closely enough to be accepted, and
  differs in how a multi-way source construct is represented in its states;
- the blocked run differs in the dispatch mechanism itself.

None of that is visible in a tool's exit code, and none of it is visible in the
output graph. It is visible in the successor score, in the ground-truth region
map, and in eight hex digits of program output.

## Studio: audit a beautiful result

Static analysis only. Do not execute the incorrect rewrite — you already know
what it prints, and the exercise is to find the fault without that.

1. In the clean listing, identify the four `switch` alternatives and the block
   they all reconverge to.
2. In the rewritten listing, find the block that contains all four. Walk it
   instruction by instruction and compute what it returns for an input whose
   low two bits are `01`. Compare with the clean path for the same input.
3. Find the four identical state stores and say what their repetition tells you
   about how the recovery went wrong.
4. Now the assessment skill. Write the rejection: a paragraph that refuses the
   claim "this rewrite deobfuscated the function", citing the successor score,
   the region map and the block listing — **without** citing the runtime
   output. That is the position an analyst is usually in.
5. Finally, the counterfactual. What would the tool have had to represent
   differently to get this right? One sentence.
