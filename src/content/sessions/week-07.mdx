Last week ended with a hand argument and a hole in it: the product of two
consecutive integers is even, *over the integers*, and the machine works modulo
2³². This week we stop arguing and write the obligation down.

<section class="sc-section">

## Symbolic execution, in one paragraph

Instead of running the function on a value, run it on a *variable*. Every
instruction updates an expression rather than a number: `and eax, 1` turns the
expression in `eax` into `bvand(previous, 1)`. When you reach a conditional
branch you have an expression for its condition, in terms of whatever you left
symbolic. Then you can ask a solver about it.

What you left symbolic is the whole ballgame. Here, the two globals the
predicate reads are symbolic — nothing else about the program's state is. That
choice is the analysis's model, and every result below is a result *about that
model*.

</section>

## Two queries

Write `P` for the path prefix and `C` for "the branch is taken". Then there are
exactly two things to ask, and they are separate questions:

<Queries>
  <Query
    obligation="P ∧ C"
    status="SAT"
    tone="info"
    reading="The taken direction is reachable within the model, and here is a state that reaches it."
  >
    The solver returns a model: both globals zero.

    ```json
    "model": { "g_140089018_4": 0, "g_14008901c_4": 0 }
    ```

    That is a witness *inside the model*. It is not automatically a reachable
    whole-program input, because nothing here checked that those globals can
    hold those values at this point in a real execution.
  </Query>
  <Query
    obligation="P ∧ ¬C"
    status="UNSAT"
    tone="pass"
    reading="No assignment to the symbolic globals makes the branch fall through — so under P and this model, that edge cannot be taken."
  >
    No model, because there is none. This is the result the rest of the block
    is built on, and it is the one most often quoted more strongly than it
    deserves.
  </Query>
</Queries>

The prefix here is trivial — `(= (_ bv1 1) (_ bv1 1))`, which is to say "no
constraints", because the gate is reached unconditionally. The file records it
anyway. On a gate deeper in the function it would not be trivial, and a result
whose prefix was not written down would not be interpretable at all.

:::warning[Three statuses, three meanings]
**SAT** — there is a model. For an equivalence-disequality query that model is
a counterexample *within the model*, not necessarily a reachable input.
**UNSAT** — no assignment satisfies the formula under its assumptions. For a
faithful encoding this establishes the property in scope; under *inconsistent*
assumptions it establishes nothing, because everything follows from a
contradiction. **UNKNOWN or timeout** — neither. It is not a weak yes.
:::

The false-positive count is the number that makes the rest mean something. A
classifier that called everything opaque would score 38 out of 38 on the
injected gates and be worthless. The genuine conditions staying two-sided is
the control.

The aggregate across all four `-O0` lanes is 38 true positives, 1 false
negative, 0 false positives, 16 true negatives, and 2 branches never reached
within the exploration budget. All three of the shortfalls — the false negative
and the two unreached — are in one lane, and that lane is the subject of the
next section.

## The assumption that changes the answer

One implementation's opaque conditions are not algebraic. They are built from
program state that gets initialised at start-up, and its generated C says so
in the clear.

    note="where the state came from"

  <span slot="caption">
    Same harness, same branches, same day. Read the left pane's `failure`
    block: the run did not fail to prove the gates, it *stopped* — at
    `mov eax, dword ptr [rcx + rax*4]`, a symbolic effective address, with the
    policy `"stop, no unrecorded concretization"`. Given an unconstrained
    pointer it declined to guess. The right pane is the alternative: emulate
    the real initialisation path for 763 instructions, capture the state, keep
    the function's two arguments symbolic, and the same three gates fall out.
    The difference is not a technique — it is an assumption about the world,
    made explicit and written to a file.
  </span>
</CodePair>

That stopping policy is worth dwelling on. An analysis that silently
concretised the pointer would have produced a number, and the number would have
been about one arbitrary heap layout while looking like a general result. The
configuration records `"symbolic_address_policy": "stop, no unrecorded
concretization"` because refusing to answer is a defensible result and a quiet
guess is not.

Which means the honest statement of the right-hand result is long, and the long
version is the only correct one: *under the captured initialised state, with
the function's arguments still symbolic, three injected gates are one-sided.*
Not: these predicates are opaque. Allocation outcomes, heap layout, entropy sources
and any later mutation of those globals are all outside the model, and a claim
about arbitrary program state is a different claim that this evidence does not
support.

## Studio: interpret a proof you did not run

Nothing is executed this week. The solver artefacts are frozen and that is the
point — you are practising the thing an analyst actually does, which is reading
somebody else's result and deciding what it licenses.

1. Open `prefix.smt2`, `condition.smt2`, `true.smt2` and `false.smt2`. Identify
   which assertion differs between the last two, and say in one sentence what
   each file is asking.
2. Write the two obligations for this gate in your own notation, including the
   bit widths. Then write the sentence that correctly reports the result — the
   long version, with the qualifiers.
3. Now write the overclaimed version, the one that drops the prefix and the
   model. Keep both. A2 asks you to spot the second kind in somebody else's
   prose.
4. Compare the two Tigress result files. State the assumption the right-hand
   one adds, and list three things it still does not cover.
