The solver's job finished last week. Nothing it did changed a file.

What happens now is a different program: a patch consumer that reads the frozen
proofs, checks the bytes it is about to touch against what it expects to find,
and writes a new executable. It ran no solver queries of its own — the
recorded count is zero — and that separation is the reason this week's result
can be stated cleanly.

## Six bytes

<BytePatch

    { label: "after", bytes: ["E9", "06", "00", "00", "00", "90"], changed: [0, 1, 2, 5], asm: "jmp 0x140001672 ; nop" },
  ]}
/>

Work out the displacement, because it is the whole trick. `0F 85` is a
two-byte opcode for `jne rel32`, so the instruction is six bytes long and the
next instruction begins at `0x166D`; a displacement of `0x05` reaches
`0x1672`. `E9` is a one-byte opcode for `jmp rel32`, so *that* instruction is
five bytes long and the next one begins at `0x166C`; to reach the same
`0x1672` the displacement has to be `0x06`.

Same destination, different number, because the length of the instruction
changed. The sixth byte would otherwise be a stray tail, so it is filled with
`0x90` — a one-byte `nop` — which keeps every subsequent byte in the file at
the address it was at before.

That is why four bytes differ out of six, and it is also the arithmetic behind
the file-level number:

## What the rewrite did not touch

<EvidenceCode
  id="assets/evidence/s03_ollvm_bcf/metadata_audit.json"
  lang="json"
  title="metadata_audit.json — the layout audit"
  note="every claim here is a checked file-level fact"
  from={1}
  to={13}
  class="sc-wide"
/>

Headers identical. Sections identical. Imports, exports, relocations, exception
and debug directories identical. The target's entry and unwind ranges
identical. No byte outside the approved window changed.

That is a *layout-preserving* rewrite, and it is a design choice with a cost.
Nothing was deleted, nothing moved, and every unreachable instruction is still
physically present in the file. The alternative — recompacting the function —
would produce a smaller binary and would invalidate every address in it.

Read the last two fields of that record with care:

:::warning[Two things the audit explicitly does not claim]
`"pdb": "Not copied. Retained original RSDS debug reference is provenance
only, not a valid changed-instruction map."` The original debug identifier can
still match after patching, so a debugger will happily load symbols whose
instruction mappings inside the rewritten function are now wrong. Decline them.

`"exception_unwind_correctness_tested": false`. The unwind ranges are
byte-identical, and nobody tested whether an exception unwinding through a
patched frame behaves correctly. Ordinary execution is not an unwind guarantee.
:::

</section>

Thirty-three blocks became unreachable: eleven bogus clones and twenty-two jump
stubs. Note the two zeroes. Zero *predicate computation* blocks became
unreachable — the arithmetic that computes each opaque condition still runs on

blocks became unreachable, which is the check that the rewrite did not remove
program logic.

The same workflow, unmodified, on the second implementation: sixteen gates
proved, sixteen patched, sixty-four bytes changed, reachable blocks 54 to 30,
4,598 triples, zero mismatches. That transfer is the strongest generic result
in the course, and it is worth being exact about what made it transfer — the
proof was about instruction semantics and the patch was about bytes. Neither
step recognised an obfuscator.

:::info[9,189 inputs is not all inputs]
Together the two families cover 9,189 differential triples with no mismatch.
That is strong evidence and it is evidence of a specific kind: the program
agreed with its comparators on the inputs that were run. It is not a proof of
equivalence, the solver proofs were per-branch and not whole-program, and the
unwind behaviour was never tested at all.
:::

## Studio: justify a patch you did not write

1. At RVA `0x1667`, derive both displacements from first principles and explain
   why they differ. Then explain why the `nop` is necessary rather than tidy.
2. Using the projection notes, reconcile three numbers: 70 physical blocks, 37
   reachable blocks, 33 unreachable blocks. Say what each one is counting.
3. Find the two zeroes in the classification counts and say what each one
   rules out.
4. Separate the evidence: which part of this week's result is a solver proof,
   which part is a byte-level argument, and which part is a test? For each,
   name the file.
5. Then the A2 rehearsal: write a one-paragraph analyst's summary of this
   week's result that is *too strong*, and underline the words doing the
   overreaching.

No new patching. The point is the justification, not the edit.
