Bogus control flow adds branches that never go both ways, guarded by
predicates whose value the transformer knows and the analyst is supposed not
to. It also clones real code, so that the branch has somewhere plausible to
go.

The target for this week and the next two was written to make the distinction
checkable. It has exactly four conditions, each with a constant you will
recognise on sight.

Every one of those four is **path-dependent**: whether it is taken depends on
the arguments, and both directions are reachable. Keep that word. An opaque
predicate is not "a branch whose outcome depends on something obscure" — it is
a branch one of whose directions is *unreachable*, by construction, and the
whole of week 7 is about how you would show that.

</section>

Read it instruction by instruction. Two `mov`s load a pair of writable globals
through RIP-relative addressing — `0x14008901C` into `eax` and `0x140089018`
into `ecx`. Then `edx = eax − 1`, `imul eax, edx`, `and eax, 1`, `cmp eax, 0`,
`sete al`. That is the algebraic half: **g · (g − 1) & 1 == 0**. The other half
is `cmp ecx, 0xa` / `setl cl` — a signed comparison of the second global
against ten. `or al, cl`, `test al, 1`, and the `jne` at `0x1667` goes to the
real code while the fall-through goes to a stub.

So the gate is a disjunction, and its first disjunct is the interesting one:
the product of two consecutive integers is even, so the low bit is zero, so the
`sete` always sets `al` — which makes the whole `or` always true and the branch
always taken.

*Over the integers.* Over 32-bit values with wraparound you would want to
check, and "I can see it is always true" is not a check. Week 7 stops looking
at it and proves it instead.

Note also why the globals are there at all. A predicate over initialised
constants would fold away during compilation. A predicate over *writable*
globals cannot be folded, because the compiler cannot prove that nothing
writes them — which is the same fact the analysis in week 7 has to work
around.

</section>

## Four implementations, four different amounts of nothing

<LectureTable id="04_opaque_optimization" class="sc-wide" />

One row on that table needs unpacking, because it is the week's most useful
correction.

One implementation's `-O0` IR has the *same* 44-block / 69-edge topology as the
specimen above. Its machine code has 15 blocks and 18 edges. The reason is
that most of its injected guards are literal `icmp eq i32 1, 1`, and the
backend folds those without being asked. The four conditional jumps that
survive into its machine code are **the four genuine source conditions**.

So when the week 7 workflow runs on that binary and proves zero injected gates,
that is not a failure of the workflow. There were no injected gates left in the
machine code to prove anything about. Crediting those four surviving branches
as "removed injected predicates" would invert the result completely — and it is
exactly the kind of mistake that a workflow reporting only successes would
make.

</section>

## A different mechanism: state, not algebra

One implementation in this corpus builds its opaque conditions from
**runtime-initialised program state** rather than from an algebraic identity —
source-level guards over globals set up at start-up.

## Studio: separate the genuine from the injected

Working from the clean and treated disassembly of the same function:

1. Find all four genuine conditions in the treated listing. Give the address
   of each. Say what you used to identify them.
2. Find one injected gate. Write out the predicate it computes, as algebra,
   from the instructions.
3. Now argue that your predicate is always false — and then find the hole in
   your own argument. The hole is the reason week 7 exists.
4. Read the family results file and find the lane where zero gates were
   proved. Write one sentence explaining why that is not a failure of the
   prover, citing the block counts.
