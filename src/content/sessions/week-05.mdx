Week 3 ended with a transformation that mostly stopped existing when the
optimiser was turned on. That was not an accident of that tool. Optimisation
level is not a nuisance variable in this field — it is part of the treatment,
and this week is about designing comparisons that survive it.

<section class="sc-section">

## How the matrix controls for it

Two different problems, two different answers.

For the **source-level** lane the problem is easy to state and easy to get
wrong: if you generate obfuscated C four times, once per optimisation level,
you have four specimens and no control. So the matrix generates the C **once**
and compiles that exact file at every level. Here is the check, in the two
retained metadata records:

For the **IR-level** lanes the problem is the opposite. If you run the
obfuscation pass and then hand the result to a normal compilation, the
middle-end runs twice and you cannot tell what the pass did from what the
second run did. So the matrix emits post-pass IR once, then generates object
and assembly from that exact IR with `-Xclang -disable-llvm-passes`. One
middle-end run, per build, on purpose.

</section>

The absolute count nearly halved. The ratio against the correct comparator
barely moved. Both statements are true, and only the second one is about the
transformation.

That last number carries a warning worth repeating. An earlier measurement of
the clean `/Ox` target overran the function boundary — it measured to the next
export rather than to the return — and produced a larger clean figure and
therefore a smaller, flattering ratio. The corrected comparator is 106
instructions. If you are ever tempted to compare against a number you did not
scope yourself, that is the shape of the mistake.

:::warning[Two numbers, two questions]
"Did optimisation shrink the obfuscated function?" — yes, 426 to 226.
"Did optimisation weaken the obfuscation?" — barely, 1.7× to 2.1× against the
matched clean control. These are different questions with different answers
and the same two measurements behind them.
:::

## What disappears

Now the result that ought to make you nervous about every `-O0` finding in the
literature.

<LectureTable id="04_opaque_optimization" class="sc-wide" />

Two of the four opaque-control-flow lanes are **gone** by `-O1`. Not reduced —
the measured target is structurally identical to the clean target. One of them
was already mostly folded at `-O0`, because its injected guards were literal
`icmp eq i32 1, 1` and the backend does not need an optimiser's permission to
resolve that.

For arithmetic, the same pattern with different winners:

<LectureTable id="03_arithmetic_optimization" class="sc-wide" />

And for flattening, the opposite result entirely:

<LectureTable id="05_flattening_optimization" class="sc-wide" />

Flattening is the durable family. Two implementations keep essentially their
whole dispatcher from `-O1` through `-O3`; a third loses about half its
structure and still has a dispatcher; the source-level one changes *how* the
dispatch is lowered — an indirect jump table at some levels, a direct
comparison network at another — without losing the state machine at all.

That last point is the one people get wrong. A missing indirect jump is not
evidence that flattening disappeared. It is evidence about lowering.

</section>

## What this does to course design, and to yours

The study's own recommendation is blunt: teach bogus control flow with explicit
`-O0`-versus-`-O2` pairs, because two of the four implementations vanish at
`-O1` and presenting their `-O0` structure as "an obfuscated binary" would be
straightforwardly false.

Which is why weeks 6 to 8 work on `-O0` specimens and say so in every
sentence, and why week 10's flattening work can use higher levels.
