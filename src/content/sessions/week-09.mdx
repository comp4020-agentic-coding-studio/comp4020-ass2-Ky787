Everything so far hid a *value* — what an expression computes, or which way a
branch goes. Flattening hides something else: the edges. Every semantic block
still exists and still does its job, and no block any longer says which block
comes after it. That fact is now held in a number.

An if/else on parity. A four-iteration loop with a condition inside it. A
four-way `switch` on the low two bits whose cases all reconverge. Then a final
XOR against `0xCAFEBABE`. The clean build of that is 21 blocks and 26 edges,
and you could sketch it from the source.

There is the whole mechanism, in one construct. A `switch` on the state
variable, with a case per semantic region and an apparently arbitrary 32-bit
constant per case. Each semantic block ends by *storing a new state* and
jumping back to the dispatcher instead of jumping to its successor.

The constants are the interesting part. They are randomised, so they carry no
ordering information: state `0x51837FD6` does not come "before" state
`0x03AD94FD` in any sense the number reveals. The successor relation now lives
in the *stores*, distributed across the function, one per exit edge.

</section>

Read that table as a control-flow graph and the source is back: a two-way
branch that reconverges. Nothing about the *machine code* draws those edges.
They are consequences of which constant gets stored, which is why recovering
them is a semantic problem — you have to know what the state variable holds
when the dispatcher is reached, which means reasoning about the computation,
not matching a pattern.

:::info[No indirect jump required]
In this build the dispatcher is a ladder of comparisons and direct branches,
not a jump table. The LLVM backend lowered a sparse `switch` over randomised
32-bit constants that way. A flattened function with no indirect jump is still
flattened — the state machine is in the state variable, not in the opcode.
:::

## Studio: follow one transition

Do not try to reconstruct the whole function. Pick one region and follow it
properly — that is the exercise, and A2 is the same skill under a deadline.

1. In the flattened IR, find the `switch` and list the state constants it
   selects between. Say where the state variable lives.
2. Take the parity branch. Find the two state stores that implement its two
   outcomes, and the state both of them lead to.
3. Now compare with the clean CFG. Say which clean edge corresponds to which
   state store.
4. Look at the source-level specimen's jump table. Find state 7, work out the
   address it dispatches to, and say what that region does. Then note what an
   analysis would have to resolve before it could see any of those 21 edges at
   all.
