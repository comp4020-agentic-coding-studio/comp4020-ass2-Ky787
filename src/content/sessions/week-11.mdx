Lifting runs the pipeline backwards. Take a compiled function, translate each
instruction into an intermediate representation with defined semantics, and you
have something an optimiser can simplify, a solver can reason about, and a
person can read.

It is the most appealing idea in the field, and week 11 exists because of what
that appeal does to your judgement.

Seventeen functions lifted. Four stage variants each, so sixty-eight modules,
and every one of the sixty-eight passed the LLVM verifier and recompiled.
Fifty-one stages were actually executed against test vectors — 218,334 vectors
in total — and forty-seven passed.

Thirteen cases passed under their documented runtime contracts. One case
failed. Two bogus-control-flow lifts were never executed as lifts, because
they contained unknown helper calls and memory accesses with no safe contract
to run them under; and the post-link lane stayed static-only, because nothing
it produced ran in the first place.

Note what "68 verified modules" is a fact about. It is a fact about
well-formedness.

</section>

## Four stages, two paths

The stage names matter, because reading them as one chain leads to a wrong
conclusion about where a bug came from.

So there are two branches from R — `R → R2` and `R → M → M2` — and they are
alternatives, not a four-step sequence. If a defect is present in R, it is
present before either branch, and neither ordinary optimisation nor the
lifter's own can be blamed for introducing it or expected to remove it.

</section>

## The case that passes

<Specimen
  title="Lifting the MBA specimen"
  fields={[

    ["Lift time", "0.047 s"],
    ["Sizes", "6,689 raw IR instructions → 386 at R2, 375 at M, 359 at M2"],
    ["Runtime", "all 4,118 vectors match at every one of the four stages"],
  ]}
  verdict={{ tone: "pass", text: "PASS", label: "retained runtime status" }}
/>

That is a genuine success and worth being precise about. An earlier
expression-extraction attempt on this same function gave up: it hit a
20,000-node AST occurrence guard at 25,384 occurrences. The lifter produced a
compact, executable whole-function representation of it in 47 milliseconds.
Different tools, different representations, and this one scaled where the other
did not.

And then read the residue. M still contains 372 arithmetic and Boolean
instructions where the clean build's equivalent is a short scalar expression.
Some constants are recognisable; hundreds of multiply, add and Boolean
operations with coefficients are not. This is successful lifting with runnable
partial simplification — not MBA elimination, and not recovered source.

One detail to head off a misreading: M2 contains thirteen `call` instructions,
and they are LLVM vector-reduction intrinsics introduced by vectorisation, not
unresolved calls into the original binary.

</section>

Forty-five instructions. Smaller than the machine code, readable, verifier
clean, and wrong for 95% of its inputs.

### Where it came from

The cause is identifiable in the lifter's source without patching anything.
Its operand utilities fold

```text
(~A & B) | (A & C)   →   select(A, C, B)
```

when the known-bits extrema of `A` are zero and all-ones. That is a legitimate
rewrite when `A` really is a mask that is either all-zeros or all-ones. But an
*unconstrained* integer also has those extrema, and having them does not make
`A` a mask.

<Queries>
  <Query obligation="A = 0 or A = −1" status="fold is sound" tone="pass" reading="A is a genuine mask; select is exactly equivalent.">
    Which is the case the rewrite was written for, and it is common in compiled
    comparison code.
  </Query>
  <Query obligation="A = 1, B = 0, C = 2" status="fold is wrong" tone="fail" reading="Bitwise gives 0; the select gives 2. One counterexample, three small integers.">
    `(~1 & 0) | (1 & 2)` is `0 | 0` = **0**. `select(1 ≠ 0, 2, 0)` is **2**.
  </Query>
</Queries>

The emitted `%selectEZ…` values and the propagated `select` chain in the IR
above are consistent with exactly that fold. Three points of discipline about
that sentence:

1. **It is a diagnosis, not a repair.** No fix was applied and no retest was
   run, so this is a strongly supported explanation and not a verified one.
2. **The obfuscator is not at fault.** The native binary passes all 4,118
   vectors. The error appears only in the lift.
3. **LLVM is not at fault.** R already fails. Ordinary `-O2` did not introduce
   this and could not have removed it — an optimiser preserves the semantics of
   the IR it is given, including wrong semantics.

:::error[Valid IR ≠ correct lift]
Verifier acceptance means the module is well-formed: types check, SSA holds,
terminators exist. It says nothing about whether the module computes what the
machine code computed. On this site that is not an abstract warning — it is one
retained case, four stages, 3,917 mismatches each.
:::

## Studio: two verdicts from one tool

1. Draw the two stage paths. Then say, for the failing case, which stage the
   defect is in and what that rules out.
2. In the failing IR, find the eight `icmp eq` comparisons and say what the
   original function did with those eight constants. Explain in one sentence
   how a chain of additions became a chain of equality tests.
3. Evaluate `(~A & B) | (A & C)` and `select(A, C, B)` for `A = 1, B = 0,
   C = 2`. Then find a second counterexample of your own.
4. For the passing case, compare the four instruction counts and the residual
   arithmetic. Write the sentence that correctly reports it — including what it
   did *not* recover.
5. Then the capstone rehearsal. For each of the two cases, name the level the
   claim was validated at, and the level it was *not*.
